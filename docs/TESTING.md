# Testing

The test suites and what each one proves, how they are found and run (and the mutation
runs `npm test` never makes), the headless canvas that lets a visual change be checked
without a browser, every screenshot tool with its flags, the harness modules the suites
share, how to hunt something that flashes, and what was checked once -- in scratch or in a
browser -- and is not re-checked by any suite. Read this when adding a suite, when one
fails, when something is reported to flash or pop, or before calling any visual change
done. See also:
[ARCHITECTURE.md](ARCHITECTURE.md) (the
`test-perf` and `test-scaling` numbers), [BUILD.md](BUILD.md) (`--smoke`, proving the
packaged exe boots), STATUS.md.

## Running them

```bash
npm test                  # every fast suite, one after another
npm run test:all          # all of them, including the optimality sweep
npm run test:deep         # test-reach at 20 million transitions instead of 1 million
```

The runner prints how many suites ran and passed; this doc does not keep the count.
`test-optimal` is the slow one -- several minutes, single core -- and the only one
`npm test` skips (the `SLOW` set in `tools/test-all.mjs`). The fast run was last run whole
at 7c13298 on 2026-09-23: 28 suites, all passing, in 438 s (STATUS.md).
The round of 2026-09-24 then added twelve suites and rewrote `test-milestones`, and no
whole run has been made since. Timed one at a time on 2026-09-28, with other agents' node
processes running beside them, the twelve took about 240 s between them without
`test-callouts` (which threw two checks in from d55aefb until 4041664; see its row): `test-gameover`
54 s, `test-fallclear` 54 s, `test-afterimage` 46 s, `test-boardwarm` 33 s, `test-replay`
20 s, `test-menu` 16 s, `test-steady` 6 s, `test-web` and `test-sfx` 4 s, `test-lament`
9 s (2 s until its broken versions were built in), `test-gamepad` under a second (and `test-milestones` under a second). So a whole
fast run is now roughly the 438 s plus those four minutes, unmeasured as a whole; the
runner prints its own total.
`test:deep` is `test-reach` at 1,000 seeds x 20,000 floors instead of its default 200 x
5,000.

The runner starts each suite with no arguments, so the mutation runs some suites carry
behind a flag are never part of `npm test`; run them by hand after changing what they
guard:

```bash
node tools/test-replay.mjs --mutants        # each of its 45 mutants in its own process, one after another; each must fail
node tools/test-replay.mjs --mutant=NAME    # one of them; must exit 1
node tools/test-racetower.mjs --mutants     # its 23 mutants, about 2 min; each must fail
node tools/test-replayui.mjs --mutants      # its mutants, 20-50 s each; each must fail
node tools/test-menu.mjs --mutations        # each check against a broken copy of src/ (about a minute more)
node tools/test-feel.mjs --mutants          # JUMP SPEED, LOW LATENCY, PLATFORMS and DIFFICULTY: each of its 35 mutants must fail (~1 min)
node tools/test-tapjump.mjs --mutants       # the jump buffer through the air: each of its 11 mutants must fail (~25 s)
node tools/test-ascension.mjs --mutants     # ZENITH's ascension: each of its 7 mutants must fail (~30 s)
node tools/test-fallclear.mjs --mutate=NAME # cut, noburn, nofade, streakcut, streakstay, sparkcut,
                                            # sparkstay, floatercut, compstay, oldcam, compfloat: each must FAIL
```

`test-afterimage` needs no flag: its mutants run on every run (its section 10), each a copy
of `src/` with one line broken. Two suites record what they compare against from an OLD
tree: `test-menu --baseline`, run in a tree from before the menu's skin, writes the old
layout to `tools/menu-layout.json`; `test-gamepad --golden=<path to an old input.js>`
prints the keyboard trace that `KEYBOARD_TRACE` pins.

Timings inside a suite move with whatever else the machine runs. `test-boardwarm` holds the
scoreboard's warm-up to its budgets on this machine's clock (checks 3 and 4): the p99 of a
painting frame within `BOARD_WARM_MS` (0.5 ms) in play and `BOARD_IDLE_MS` (2 ms) on the
menus -- measured 0.37 and 1.88 on 2026-09-28 -- and no single slice over 0.5 ms. With
another process loading the machine a correct tree can fail them. Before believing that
failure, run the suite again alone; its structural checks (1, 2, and 4's counts and pixels)
do not move with the load.

`tools/test-all.mjs` DISCOVERS suites by globbing `tools/test-*.mjs`; do not add a list
anywhere. A new suite joins the loop the moment it exists: name it
`tools/test-<name>.mjs` and exit non-zero on failure, and that is the whole
registration (`test-walls` and `test-sparks` joined exactly so). The hand-written list
that used to live in the docs silently skipped `test-perf` for weeks, because the line
continuation in it was a literal backslash-n
rather than a newline. A passing suite prints one line and only a failing one prints its
full output -- a wall of output nobody reads is how a failure gets scrolled past.

## What each suite proves

Several exist because of specific bugs and are regression guards: `test-physics` pins
the speed-cap behaviour a review flagged as a defect (the local model's, see
[../DELEGATION.md](../DELEGATION.md)), `test-themes` enforces the contrast rule the
generated palettes broke, `test-reach` includes a same-wall-run limit after a generator
bug stacked 33 platforms up one edge, and `test-botskill` audits the demo bot against
every mechanic a player has -- a bot that never wall-bounces and never air-jumps is
climbing a ladder, not showing off the game.

The suites written on 2026-09-24 share a shape: each says in its header what it holds the
code to and why, stages real play (usually the attract bot, see [BOT.md](BOT.md)) rather
than calling the function that decides, and was run against a copy of `src/` broken the
way each check guards against -- the mutants are listed in the suite or in the commit that
added it. Where a row gives a time, it is how long the suite took alone on 2026-09-28.

## Looking at it without a browser

This matters more than it sounds. Three separate defects in this project were invisible
in a downscaled browser screenshot and obvious the moment one was rendered headlessly.

Visual changes are checked **without a browser**: `tools/headless.mjs` implements the
slice of the canvas API the renderer actually uses (a couple of hundred `fillRect` call
sites across `src/render` and `src/ui`, a few dozen `drawImage` -- count them with a grep
rather than trusting the header's "under twenty", which predates the walls, the floors,
the streaks and the trail -- and a few transforms) against a pixel buffer. It is not a
conformance-grade canvas -- strokes are approximated and arcs are filled circles -- but
everything that matters, the world, the sprites, the HUD and the screens, is rectangles
and images, and those are exact. It blends source-over with
the destination's own alpha, as a browser does, so a translucent tile pre-rendered onto
transparency comes out at its real brightness; it crops an image hanging off its edge;
and it has an `Image` that loads PNGs from the repo synchronously, so a shot shows the
artist's tiles where the game would. Four things it does NOT do as a browser does, so no
headless shot can show them: it never smooths (a fresh canvas left with
`imageSmoothingEnabled` on blurs pixel art in a browser and not here), `putImageData`
does nothing, a gradient is sampled in device pixels, ignoring the transform, and it
ROUNDS a `drawImage` destination box to whole device pixels, which a browser does not.
At zoom 1 and 2 everything lands on whole pixels anyway; at 1.75, 1.5 and 1.25 an art
pixel is a fractional number of device pixels, and which art column a device column
at the edge of a shape samples depends on that rounding -- so `test-sprites` checks the
Duke's soles by rows and only over columns INSIDE a sole, never at its edge.

It composites three of the browser's operations: plain `source-over`, and the two the
death's burn uses on its own layer (`renderer.js` `drawBurning`) -- `source-atop` and
`destination-out` -- drawn through a scratch layer so the ordinary drawing loops stay as
fast as they were (the first version tested the operation per pixel and slowed every
headless frame; see *Compositing that slowed every frame* below). Any other operation is
drawn as `source-over`. `test-fallclear` checks the two against the canvas spec, pixel for
pixel, before it trusts a frame of the burn. It has `clearRect` now (the burn layer
clears the rows it redraws); setting a canvas's width clears it too, here as in a
browser, which is how `drawHudExit` in `screens.js` clears the HUD's fade layer.

And one thing it has that a browser does not: every canvas here keeps its pixels in a
`data` array. Game code that reads `canvas.data` works in every suite and throws in the
game -- which is how the prestige badge came to be drawn nowhere but here (*A field only
the headless canvas has*, below). Measure pixels while you still hold the `Pix` or the
buffer that made them, never off a canvas.

One more bites scratch scripts rather than the game. Setting a width or height makes a
NEW pixel buffer and drops the cached context, where a browser's context carries on: a script that
took `getContext('2d')` before the `Renderer` constructor sized the canvas draws the HUD
into a dead buffer, and every frame comes out with no HUD at all. Take the context after
anything that sizes the canvas, and check a frame for the HUD's fixed furniture (the
score, the floor number) before trusting what its HUD shows.

`node tools/shot.mjs` writes a real frame to a PNG: about 0.15 s when the tool was
written at PX=2, and roughly four times that now (see below). `node tools/test-perf.mjs`
reports where the frame time goes.

`shot.mjs` renders a real 1920x1080 frame through the real renderer. It costs 4x what
it did at PX=2 -- the whole headless suite went from 35 s to about 160 s.

`smoke.js` is the same idea one level up: it starts the actual Electron app with the
window rendering OFFSCREEN and audio muted at the Chromium level, so the packaged build
can be proved to boot, serve its modules over `vytis://` and paint a frame without a
fullscreen window taking over the display or the march starting up unannounced. "It
builds" and "it runs" are different claims -- a valid exe can open a black window
because one module 404ed behind a custom scheme. The installed exe does the same with
`--smoke`; see [BUILD.md](BUILD.md).

`shot-text.mjs` exists because an announcement lives 1.6 seconds, so a screenshot taken
at a fixed time almost never catches one -- "is the announcement legible" was a question
nobody could answer. It also forces the LONGEST line in each list, which is where
overflow would show.

### Every shot tool and its flags

Each is one short node process against the headless canvas -- `smoke.js` aside, which is
Electron -- and writes a PNG to the current directory unless noted. Most draw through the
real renderer; `shot-poses` and `shot-shields` draw from the character grids the game
blits, `shot-compfeet` through the companions' own blit (`drawCompanion`) onto a zone's

## Hunting something that flashes

When something is reported to flash, blink, pop or "appear and disappear" at a moment of
play -- the death, a zone change -- no tool in this repo will show it: each draws one
frame per shot, `--frames --every` samples at 0.35 s, and a three-frame event or a camera
plunging at terminal velocity falls between. The method that found every cause at the
catch (71977f0, a43d41e) is in the `headless-canvas-fidelity` skill. That harness was
scratch; `tools/test-fallclear.mjs` is the method built into a suite for the fall -- real
deaths staged by the bot, 240 Hz steps and 160 Hz frames, the simulation and the drawing on
separate seeded streams under one fake clock, each class of thing rendered alone and
diffed against the frame before with the camera lined up -- so start from it. In short:

- **Every frame at the display rate.** Step the simulation at its fixed 240 Hz and draw at
  1/60 and 1/160, handing the HUD in exactly as `main.js` does per state (above: the tools
  do not). At 60 Hz against 240 the interpolation weight is always 0, which hides every
  stale-previous-position bug, so run both. Log, per frame, what each overlay keys on
  (alphas, counts, flags, the camera, the shake) and table the biggest one-frame change of
  each: that named every culprit at once.
- **Diff with the camera lined up.** Stub the backdrop to black, turn off the screen-space
  overlays, shift the previous frame by the camera's move (the rounded translate plus the
  shake) and count what still differs outside a box round the Duke. Check a still camera
  gives near zero first: here the walls lit up every frame, and that was the harness
  setting the eased arena width and not the stepped one.
- **Seed per tree and stage naturally.** Seed the simulation and the drawing (`Math.random`,
  which the streaks spawn from) on separate streams, and advance one fake clock per
  display frame in every pass (the warm-ups' deadlines and the menu's and callouts' clocks
  read `performance.now`; the simulation itself no longer does -- the replay engine put
  the taunt timer on simulated time and the particles and lines on a seeded cosmetic
  stream of the game's own). A bot run from the ground has a companion beside him when
  he dies; a `--floor` teleport leaves them hundreds of floors below, and fires every
  scheduled greeting at once.
- **Measure a warning's episodes in play near the hazard**, not only at the reported
  moment: CLIMB!'s first fix cured the death and flickered in live play (the row in
  [GAMEPLAY.md](GAMEPLAY.md)).
